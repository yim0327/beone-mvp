# Android 장기 연속 개발 시작 프롬프트

새 Android 세션을 시작하거나 재개할 때 아래 **프롬프트** 절 전체를 작업 지시로 전달합니다. 공통 규칙은 [장기 연속 개발 운영 규칙](autonomous-workflow.md)에 있으며, 이 문서는 Android 작업선에만 해당하는 내용을 담습니다.

---

## 프롬프트

BeONE 저장소(`yim0327/beone-mvp`)의 **Android 작업선**을 장기 연속 개발 모드로 시작(또는 재개)한다. 이전 대화 내용은 알 수 없다고 가정하고, 이 프롬프트와 저장소 문서만을 근거로 작업한다.

### 1. 먼저 읽을 문서

1. `docs/development/autonomous-workflow.md`: 권한, 파일 소유권, 시작 점검, 반복 절차, 리뷰·검증·Git 규칙. 이 문서를 반드시 따른다. 최신 `origin/develop`에 이 문서가 없으면 모드를 시작하지 않고 보고한다.
2. `CLAUDE.md`, `CONTRIBUTING.md`, `README.md`
3. `docs/PRD.md`(특히 §2.3, §4.3, §4.4, FR-06, §7), `docs/decisions.md`(특히 D-08), `docs/conventions.md`, `docs/architecture.md`
4. `docs/d08-biometrics-poc.md`: 실기기 PoC 결과와 구현 참고. "구현 참고" 항목은 결정이 아니다.
5. `docs/progress/android/README.md`. 없으면 첫 작업에서 만든다.

### 2. 담당 범위와 시작

- 담당 경로와 공용 문서 수정 기준은 운영 규칙 3절의 Android 행을 따른다. `frontend/**`와 `backend/**`는 수정하지 않는다.
- 현재 Android 앱은 빈 `MainActivity`만 있는 초기 구성이다. WebView·생체인증이 구현됐다고 가정하지 않는다.
- 시작·재개 시 운영 규칙 4절의 점검을 한 뒤, 진행 중인 Android PR의 리뷰 의견과 검증 상태부터 처리하고 아래 대기열로 넘어간다.

### 3. 작업 대기열

위에서부터 실행할 수 있는 작업을 고른다. 1·2번은 같은 FR-06 범위이므로 한 기능으로 묶어도 된다(운영 규칙 5절).

1. **네이티브 생체인증과 기기 PIN 대체 인증**
   - D-08에 따라 `BiometricPrompt`에 `BIOMETRIC_STRONG | DEVICE_CREDENTIAL`을 지정한 단일 프롬프트를 쓴다.
   - 성공·실패·취소, 그리고 인증 수단 설정이 없을 때 활성화하지 않고 설정 안내를 하는 상태를 구분한다(PRD §4.3).
   - 의존성은 안정판만 쓰고 버전과 출처를 기록한다.
2. **60초 활성화 상태**
   - 단조 시간(`SystemClock.elapsedRealtime`)으로 관리한다. 대상: 활성화, 만료, 재인증 시 재시작, 실패·취소 시 즉시 비활성화
   - 앱이 백그라운드로 가면 즉시 비활성화하고 복귀 시 재인증을 안내한다(D-08).
   - 회전·폴드·테마 변경처럼 화면 구성만 바뀌는 경우는 앱 이탈로 보지 않는다. 화면 재생성 중 인증 결과가 유실되지 않게 한다.
   - 시간·생명주기 로직은 단위 테스트로 검증한다.
3. **WebView**
   - 아직 정하지 않은 것: release 빌드에서 React 화면을 불러오는 방식(앱 번들 에셋 또는 원격 주소)과 신뢰할 origin. 사용자 결정이 필요하다.
     - 이 결정 전에는 origin을 설정값으로 분리해 둔다. debug에서는 개발 서버 주소, 테스트에서는 계측 테스트용 HTML로만 검증한다.
     - PoC의 `WebViewAssetLoader`·`appassets.androidplatform.net` 방식은 `docs/android/`에 `후보`로만 기록한다.
     - 프런트엔드 빌드(`npm ci`, `npm run build`)를 실행하거나 그 산출물을 복사하지 않는다.
   - 허용 스킴과 페이지 탐색을 제한하고, 개발용과 출시용 설정을 분리한다.
     - 원격 디버깅과 개발 서버 주소는 debug 빌드에만 둔다.
     - release 빌드에서는 평문 HTTP를 허용하지 않는다.
   - SSL 오류를 무시하지 않는다.
   - 신뢰하지 않는 origin에는 브리지를 노출하지 않는다.
   - edge-to-edge의 시스템 바 inset을 처리한다.
4. **확정 계약이 있는 브리지의 네이티브 측 구현과 검증**
   - 브리지 계약(메시지 이름, 필드, 방향, origin)이 확정된 경우에만 구현한다.
   - 계약이 없으면 `docs/android/`에 `후보`로 표시한 계약 초안과 네이티브 내부 테스트만 진행하고, 사용자 확인 사항에 올린다. 임의로 공개 계약을 확정하지 않는다.
5. **자동 테스트, 보안 점검, 실기기 확인 목록**
   - 실제 기기에서 사용자가 확인할 항목을 `docs/android/`에 목록으로 정리한다. D-08의 남은 검증, FR-06 완료 조건이 대상이다.

### 4. 지켜야 할 경계

- 프런트엔드 화면이나 이를 대신하는 제품 UI를 만들지 않는다.
  - 테스트용 최소 HTML은 Android 계측 테스트 소스(`android/app/src/androidTest/**`) 안에만 둔다.
- 인증 결과를 서버 로그인, 카드 소유 증명, 금융거래 승인의 증거로 쓰거나 그렇게 표현하지 않는다. 앱 내 가상 결제 화면을 활성화하는 트리거일 뿐이다.
- 생체 데이터, PIN, 계정 정보, 비밀값을 다루거나 기록하지 않는다. 앱에 CODEF 키·토큰을 넣지 않는다.
- release 빌드에 디버그 기능·개발 서버 주소·로그가 새지 않게 한다.
  - release 설정을 바꾸는 작업은 운영 규칙 7절에 따라 `./gradlew assembleRelease lintRelease`도 실행한다.
- 실제 React 연동이나 실기기 확인을 하지 않았다면 그 사실을 진행 기록과 PR에 명시한다.
  - mock·에뮬레이터 결과로 실기기 확인을 대신하지 않는다.
- 기기 보안 설정을 바꾸지 않는다. 사용자 승인 없이 개인 기기에 앱을 설치·실행하지 않는다. 에뮬레이터 생성과 SDK 구성요소 설치도 사용자 승인 뒤에 한다.
- 검증은 운영 규칙 7절을 따른다. SDK나 기기를 쓸 수 없으면 해당 검증만 환경 차단으로 기록한다.
- Android Gradle 설정은 Kotlin DSL을 유지한다. 백엔드의 Groovy DSL과 혼동하지 않는다.

### 5. 정지와 보고

- 실행할 수 있는 독립 작업이 없으면 `docs/progress/android/README.md`를 갱신하고 정지한다. 남은 작업이 병합 대기, 리뷰 대기, 사용자 결정, 환경 차단, 실기기 확인 대기뿐인 경우도 같다.
- 정지할 때는 다음을 보고한다.
  - 완료한 작업과 PR
  - 실제로 실행한 검증과 그 결과
  - 리뷰 상태
  - 사용자 확인 사항과 권장안
  - 실기기에서 확인할 항목
  - 다음에 할 수 있는 작업
