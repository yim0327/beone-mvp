# BeONE MVP PRD

## 0. 문서 상태

- 상태: 수정 초안
- 프로젝트명: BeONE
- 배포 서비스명: B:ONE
- 제출 마감: 2026-11-09
- 개발 인원: 2명
- 개발 요구사항의 기준 문서: `docs/PRD.md`
- 미결 결정의 기록 위치: `docs/decisions.md`

## 1. 제품 목표와 원칙

BeONE은 사용자가 보유한 카드 중 현재 주문과 같은 혜택 산정 기간의 예정 소비를 고려해, **월간 총예상 혜택이 가장 큰 카드**를 결제 직전에 자동 선택하는 시뮬레이터다.

사용자에게 표시하는 배포 서비스명은 **B:ONE**이다.

### 1.1 시연 사례에 맞춘 엔진을 만들지 않는다

- 미리 준비한 주문과 포트폴리오는 입력 예시일 뿐이다.
- 사용자가 주문, 카드 상태, 예정 소비를 바꾸면 동일한 엔진이 다시 계산한다.
- 내 카드 모드, 가상 포트폴리오 모드, 독립 평가 사례는 동일한 규칙·계산·최적화 코드를 사용한다.
- 특정 카드 이름, 시연 주문 또는 기대 정답에 따른 예외 분기를 만들지 않는다.
- 결과는 입력 상태와 검증된 공식 약관으로 설명할 수 있어야 한다.

### 1.2 실제 결제는 하지 않는다

실제 상점 주문 수신, NFC 통신, 실물 카드 결제 토큰, 카드사·결제망 승인, 매입, 정산은 구현하지 않는다. 결제 실행은 서비스 내부의 **모의 승인**으로 대체하며 실제 금융거래는 발생하지 않는다.

### 1.3 AI와 계산 엔진의 책임을 분리한다

AI는 약관 규칙 초안 추출, 업종 후보 제시, 설명 문구 생성을 보조한다. 실제 혜택 금액과 최종 카드 선택은 검증된 규칙을 사용하는 결정론적 코드가 수행한다.

## 2. MVP 범위

### 2.1 필수 범위

다음 항목은 모두 이번 MVP의 완료 대상이다.

- 공식 약관을 검증한 신용카드 최소 2종과 체크카드 최소 2종
- 수동 보유 카드·월간 상태 입력
- 실제 보유 카드의 KB국민카드 CODEF 연결·조회·상품 매핑
- 지난달·이번 달 거래 원장 기반 상태 산출 및 변경·취소 후 재계산
- 편집 가능한 주문과 예정 소비 최대 5건
- 결정론적 혜택 계산과 월간 총혜택 최적화
- 결제 전 자동 추천 또는 대표 카드 고정 설정
- 내부 모의 승인·취소 및 중복 반영 방지
- React 화면과 Android WebView
- Android 네이티브 생체인증 및 기기 PIN 대체 인증
- AI 약관 초안 추출, 사람 검증, 수동 작성 방식과의 비교
- 독립 정답을 사용하는 자동 평가

구현 순서상 P0와 P1으로 나누더라도 **P1은 선택 사항이 아니다**.

### 2.2 범위 밖

- 실제 NFC 결제와 오프라인 단말기 연동
- 실제 카드번호·CVV·계좌정보 수집
- 실물 카드 결제 토큰 발급
- 카드사·결제망·PG의 실제 또는 테스트 결제 승인
- 매입·정산 및 결제 후 실물 카드 변경
- 결제 중 추천 수락 또는 다른 카드 선택
- 여러 카드사 CODEF 연동
- 검증되지 않은 약관의 자동 반영
- 자체 소비 예측 모델 학습 및 고도화된 소비 예측
- 카드 상품 10~20종으로 확대

### 2.3 저장소 및 애플리케이션 구성

- Android 앱, React 웹, Spring Boot API를 하나의 Git 저장소에서 관리한다.
- Android 앱은 React 화면을 WebView로 표시하고 필요한 네이티브 인증 결과만 웹 화면에 전달한다.
- React 웹은 Spring Boot API를 호출한다.
- CODEF 연동, 혜택 계산, 카드 선택, 모의 승인은 Spring Boot 서버에서 수행한다.
- Spring Boot API의 데이터 저장소는 MySQL을 사용한다.
- Android 앱과 React 웹에 CODEF 비밀키·로그인 비밀번호를 포함하지 않는다.
- 각 애플리케이션은 독립적으로 빌드·테스트할 수 있어야 한다.

## 3. 두 가지 포트폴리오 모드

두 모드는 데이터의 출처만 다르고 **동일한 카드 선택 엔진**을 사용한다. 실제 보유 카드와 가상 보유 카드를 섞어 모두 실제 카드인 것처럼 표시하지 않는다.

### 3.1 내 카드 모드

- KB국민카드 CODEF 조회 또는 수동 입력으로 보유 카드를 등록한다.
- 실제 보유 카드를 공식 약관을 검증한 내부 카드 상품과 매핑한다.
- 상품 매핑이 불확실하거나 중복되면 사용자 확인 전까지 확정하지 않는다.
- 전월 인정 실적과 이번 달 혜택 사용액을 `실제 조회`, `사용자 확인`, `규칙 기반 추정`, `미확인`으로 구분한다.
- CODEF 승인내역만으로 카드사가 인정한 실적이나 지급한 혜택을 모두 알 수 있다고 가정하지 않는다.
- 계산에 필수인 값이 미확인이면 수동 확인을 요청하거나 `입력 조건 기준의 예상 추천`으로 제한한다. 미확인값을 임의로 0원으로 처리해 확정적 추천으로 표시하지 않는다.
- 검증된 상품에 매핑된 실제 보유 카드가 2장 미만이면 카드 간 최적 추천을 완료했다고 주장하지 않는다. 이때 CODEF 조회와 상품 매핑 상태를 별도로 표시한다.

### 3.2 가상 포트폴리오 모드

- 공식 약관을 검증한 신용카드 최소 2종과 체크카드 최소 2종을 가상으로 보유한 별도 시뮬레이션 사용자를 제공한다.
- 카드 상품과 혜택 약관은 실제 검증 자료를 사용한다. 카드의 소유 관계와 이용내역은 명시적인 가상 데이터다.
- 지난달·이번 달의 가상 거래를 원장으로 보관한다.
- 가능한 범위에서 원장과 검증된 규칙으로 전월 인정 실적, 이번 달 예상 혜택 사용액, 잔여 혜택 한도를 산출한다.
- 실적 인정·제외, 한도 소진·잔여, 거래 취소를 재현할 수 있는 포트폴리오 템플릿을 제공한다.
- 사용자가 가상 거래 또는 명시적인 수동 상태값을 바꾸면 다시 계산한다. 수동 상태값은 원장 산출값과 구분한다.
- 동일한 원장, 적용 약관 버전, 기준일에서는 동일한 상태와 결과가 나와야 한다.

가상 포트폴리오는 실제 사용자에게 해당 카드가 발급됐다고 주장하기 위한 수단이 아니다.

## 4. 사용자 흐름

### 4.1 결제 전 준비

1. 사용자가 `내 카드` 또는 `가상 포트폴리오` 모드를 선택한다.
2. 보유 카드와 월간 상태를 확인한다.
3. 결제 전에 `월간 혜택 자동 추천` 또는 `대표 카드 고정`을 설정한다.
4. 필요한 경우 추천 제외 카드를 설정한다.
5. 같은 혜택 산정 기간의 예정 소비를 최대 5건 입력·수정한다.

`대표 카드 고정`은 사용자 선택을 존중하는 방식이다. 이때도 엔진은 월간 최적 카드와 비교한 예상 혜택 차이를 표시한다.

**사용자 통제는 결제 전 설정으로 제공한다. 결제 버튼을 누른 뒤 추천 수락이나 카드 변경 단계는 두지 않는다.**

### 4.2 편집 가능한 가상 주문

1. 가맹점명, 금액, 결제 예정 일시, 업종, 결제 방식이 채워진 예시 주문을 보여준다.
2. 사용자는 모든 필드를 수정하거나 새 주문을 만들 수 있다.
3. 업종 분류가 불확실하면 사용자에게 확인을 요청한다.
4. 가맹점 전용 혜택은 해당 가맹점을 식별할 근거가 있을 때만 적용한다. 이름이 비슷하다는 이유만으로 확정하지 않는다.
5. 주문이 변경되면 기존 추천을 재사용하지 않고 다시 계산한다.

### 4.3 단일 가상카드 활성화

1. 사용자가 가상카드 화면을 열면 Android 네이티브 생체인증을 요청한다.
2. 생체인증을 사용할 수 없으면 Android 기기의 PIN 인증을 대체 방식으로 사용한다.
3. 인증 성공 시 60초 동안 `가상카드 사용 준비` 화면과 `가상 주문서 결제` 버튼을 활성화한다.
4. 인증 실패·취소 또는 60초 만료 시 버튼을 비활성화하고 재인증을 안내한다.
5. 생체인증과 기기 PIN 모두 사용할 수 없으면 기기 인증 설정이 필요함을 안내하고 활성화하지 않는다.

이 인증은 **앱 내 가상 결제 화면을 활성화하는 트리거**다. 실제 카드 소유 증명, 카드사 결제 인증 또는 서버가 검증한 금융거래 승인으로 표현하지 않는다.

### 4.4 자동 선택과 모의 승인

1. 사용자가 `가상 주문서 결제` 버튼을 누른다.
2. 서버가 최신 주문, 보유 카드, 상태, 예정 소비, 유효한 `VERIFIED` 규칙을 다시 확인한다.
3. `월간 혜택 자동 추천`이면 엔진이 카드를 선택하고, `대표 카드 고정`이면 사전에 지정한 카드를 사용한다.
4. 결제 중 `추천 수락` 또는 `다른 카드 선택` 단계를 두지 않는다.
5. 내부 모의 승인기가 선택 카드에 주문을 배정한다.
6. 승인 성공이 확정될 때만 시뮬레이션 원장과 혜택 사용 상태를 갱신한다.
7. 결과 화면에 선택 카드, 예상 혜택, 다른 카드와의 비교, 선택 이유, 데이터 출처, 규칙 버전, `모의 승인` 표시를 제공한다.
8. 취소 시 원장을 기준으로 영향을 받은 상태를 다시 계산한다.

모의 승인 실패는 서비스 내부 테스트 조건에 따른 실패다. 실제 카드사가 거래를 거절했다고 표현하지 않는다.

## 5. 기능 요구사항

### FR-01. 공식 약관과 규칙 데이터

- 공식 카드 상품설명서 또는 카드사 혜택 페이지를 근거로 신용카드 최소 2종과 체크카드 최소 2종을 선정한다.
- 첫 선정 후보에는 CODEF 계정에서 조회된 `올라운드 티타늄카드`(신용)와 `nori 체크카드(RF)`(체크)를 포함한다.
- 두 상품의 정확한 공식 상품명·상품 버전·약관·CODEF 응답 매핑을 확인한다.
- 나머지 신용카드 1종과 체크카드 1종을 선정한다.
- 첫 4종은 월간 혜택 산정 기간이 명확하고 비교 가능한 상품을 우선한다. 위 실제 보유 상품의 약관이 이 조건과 충돌하면 임의로 다른 기간 규칙을 적용하지 않고 `docs/decisions.md`에 처리 방식을 결정한다.
- 원문·출처 스냅샷, AI용 전처리 자료, AI 규칙 초안, 사람이 승인한 버전 있는 `VERIFIED` 규칙을 분리한다.
- 규칙에는 혜택 대상·제외 대상, 결제 방식, 실적 조건, 최소 결제금액, 계산 방식, 월 한도, 적용 기간, 공식 출처, 검증 상태를 기록한다.
- 기준일에 유효한 `VERIFIED` 규칙만 계산에 사용한다.
- 약관 변경 후보를 발견해도 사람의 검증 없이 계산 규칙을 교체하지 않는다.

완료 조건:

- 4종의 주요 혜택과 제외 조건을 검증된 규칙으로 표현한다.
- 모든 계산 결과에서 공식 출처, 적용 기간, 규칙 버전을 확인할 수 있다.
- 미검증·기간 만료 규칙은 계산에 사용되지 않는다.
- CODEF 실제 보유 상품 중 최소 1종이 검증된 내부 상품에 매핑된다.

### FR-02. 거래 원장과 월간 상태

- 가상 포트폴리오의 지난달·이번 달 거래를 카드, 일시, 금액, 가맹점·업종, 결제 방식, 승인·취소 상태와 함께 보관한다.
- 전월 인정 실적은 검증된 실적 인정·제외 조건에 따라 산출한다.
- 이번 달 혜택 사용액과 잔여 한도는 해당 혜택 산정 기간의 거래를 순서대로 계산한다.
- 거래일에 유효했던 약관·규칙 버전을 과거 거래 계산에 사용한다. 변경된 최신 규칙을 과거 거래에 소급 적용하지 않는다.
- 상품별 실적·혜택 기준 기간이 다르면 실제 약관에 맞는 기간을 사용한다. 지원하기로 결정하지 않은 기간 유형을 달력 월 규칙으로 임의 변환하지 않는다.
- 모의 승인·취소 후 영향을 받는 상태를 다시 계산한다.
- 중복 승인·중복 취소로 금액이 달라지지 않게 한다.
- 수동 상태값은 원장 산출값과 구분하고 출처·기준일을 기록한다.
- CODEF 실제 승인내역과 자체 모의 거래 원장은 별도로 유지한다.

완료 조건:

- 가상 거래 추가·취소에 따라 관련 실적·혜택 사용액·추천이 다시 계산된다.
- 같은 원장과 규칙 버전에서는 같은 결과가 나온다.
- 주요 상태값을 공식 약관에 근거한 독립 손계산 사례와 대조한다.

### FR-03. 카드 상태와 CODEF

- 실제 보유 카드 등록·수정과 전월 실적·이번 달 혜택 상태의 수동 입력을 제공한다.
- 각 상태값에 출처(`CODEF`, `MANUAL`, `INFERRED`, `SYNTHETIC`, `UNKNOWN`), 기준 기간, 갱신 시각을 기록한다.
- KB국민카드 CODEF 보유카드·승인내역·실적조회 결과를 공통 내부 모델로 변환한다.
- 청구내역·한도조회 결과는 필드의 의미와 계산 적합성을 확인한 경우에만 반영한다. 카드 이용한도와 월 혜택 한도를 혼동하지 않는다.
- 실제 조회된 `올라운드 티타늄카드`와 `nori 체크카드(RF)`의 내부 상품 매핑을 확인한다. 표시명이 같거나 비슷하다는 사실만으로 자동 확정하지 않는다.
- CODEF 값과 수동 값이 다르면 계산에 사용할 값을 사용자에게 명시적으로 확인받는다.
- CODEF 연결 실패·인증 만료·매핑 실패에도 수동 입력 흐름을 유지한다.

완료 조건:

- CODEF 실계정 조회 결과가 내부 모델과 사용자 카드 확인을 거쳐 동일 추천 엔진에 입력된다.
- 조회만 성공한 상태와 매핑·상태 확인을 거쳐 추천에 사용된 상태를 구분한다.
- 실제·추정·수동·가상 값을 화면과 데이터에서 혼동하지 않는다.

### FR-04. 주문과 예정 소비

- 예시 주문 표시와 임의 주문 생성·수정을 모두 지원한다.
- 주문에는 가맹점명, 금액(원), 결제 예정 일시, 업종, 결제 방식, 주문 식별자가 포함된다.
- 예정 소비에는 날짜, 금액, 가맹점 또는 업종이 포함된다. 한 번의 최적화에 최대 5건을 사용한다.
- 현재 주문과 관련 카드의 검증된 혜택 산정 기간에 속하는 예정 소비만 해당 카드의 혜택 계산에 반영한다.
- AI가 예상 소비를 제시하더라도 사용자가 확인한 건만 예정 소비에 포함한다.
- 불확실한 업종이나 가맹점 전용 혜택을 확정된 사실처럼 사용하지 않는다.

완료 조건:

- 미리 준비하지 않은 주문의 금액·업종·날짜·결제 방식을 바꿔도 추천과 근거가 재계산된다.
- 평가용 주문이 시연용 주문과 동일한 API 및 계산 코드를 통과한다.

### FR-05. 결정론적 혜택 계산과 최적화

- 기준일에 유효한 규칙에 대해 대상·제외 항목, 전월 실적, 최소 결제금액, 결제 방식, 남은 혜택 한도를 검사한다.
- 금액은 원 단위 정수로 계산한다. 약관이 허용하지 않는 한 한 거래에는 가장 큰 단일 혜택만 적용한다.
- 현재 주문을 후보 카드 각각에 배정하고, 예정 소비의 가능한 배정을 비교해 총예상 혜택이 최대인 카드를 선택한다.
- 거래 순서와 카드별 혜택 한도 소진을 반영한다.
- 이번 달 모의 거래가 이번 달에 적용할 전월 실적 자격을 즉시 높이지 않는다.
- 예정 소비가 없으면 현재 주문 혜택을 기준으로 선택한다.
- 총혜택이 같으면 현재 주문 혜택, 그래도 같으면 카드 ID 순으로 결정한다.
- 필수 상태가 불완전해 선택 카드가 달라질 수 있으면 확정적인 최적 추천으로 표시하지 않는다.
- 카드별 적용·제외 사유, 현재 주문 혜택, 월간 총예상 혜택, 잔여 한도, 차선 카드 대비 차액을 제공한다.
- 이미 확정된 모의 거래의 누적 혜택과 아직 실행되지 않은 예정 소비의 예상 혜택을 구분한다.

완료 조건:

- 현재 주문 혜택 최대 카드와 월간 총혜택 최대 카드가 다른 독립 평가 사례를 통과한다.
- 주문이나 상태를 변경하면 근거와 결과가 새 입력에 맞게 바뀐다.
- 같은 입력·원장·규칙 버전에서 같은 결과가 나온다.

### FR-06. React·Android 가상카드 UI

- React 웹 화면을 Android WebView에서 실행한다. Next.js 사용은 이번 MVP의 기술 선택에 포함하지 않는다.
- Android 네이티브 인증 결과를 웹 화면에 성공·실패·취소 상태로 전달한다.
- 생체인증을 사용할 수 없으면 Android 기기의 PIN 인증을 요청한다.
- 실제 Android 기기에서 인증, 60초 활성화, 시간 만료, 앱 복귀, 재인증을 확인한다.
- 60초 화면을 실제 NFC나 결제망 진행 상태로 표현하지 않는다.
- 서버는 생체인증 화면이 표시됐다는 사실을 실제 결제수단 인증으로 신뢰하지 않는다.

완료 조건:

- 실제 기기에서 가상 주문서 결제 버튼의 활성화·비활성화 흐름을 시연한다.
- 생체인증 불가 시 기기 PIN으로 진행할 수 있다.
- 인증 실패·취소·만료 시 재인증 안내가 작동한다.

### FR-07. 모의 승인·취소

- 선택 카드 ID와 주문 ID로 내부 시뮬레이션 거래를 생성한다.
- 승인 직전에 서버가 최신 주문 내용, 카드 상태, 유효 규칙을 다시 확인한다. 변경 전 추천 결과를 그대로 승인에 사용하지 않는다.
- 승인 성공·실패·취소 상태, 시각, 내부 식별자를 기록한다.
- 동일 요청 재전송으로 거래나 혜택을 중복 반영하지 않는다.
- 승인 성공 시 시뮬레이션 원장을 갱신하고, 취소 시 원장 기준으로 재계산한다.
- 실제 카드번호, 실제 카드사 승인번호, 실제 결제 토큰을 사용하지 않는다.
- 실제 결제망이나 카드사·PG 승인 API를 호출하지 않는다.

완료 조건:

- 정상·실패·중복 요청·취소·중복 취소를 재현한다.
- 시뮬레이션 결과와 CODEF 실제 승인내역이 섞이지 않는다.

### FR-08. AI 보조

- AI는 공식 약관에서 규칙 초안을 추출하고 필드별 원문 근거를 제시한다.
- 사람이 수정·승인하기 전에는 AI 출력으로 혜택 금액을 계산하거나 최종 카드를 선택하지 않는다.
- AI는 업종 후보와 추천 설명을 보조할 수 있다.
- AI 실패 시 사용자 업종 확인과 계산 결과 기반 기본 설명을 제공한다.
- 소비 예측은 필수 입력이 아니다. 구현한다면 사용자 확인을 거친 예정 소비 후보로만 사용한다.

완료 조건:

- 공식 약관 원문 → AI 초안 → 사람의 수정·승인 → `VERIFIED` 규칙 반영 과정을 카드 4종에 대해 기록·시연한다.
- 카드 4종에 대해 수동 규칙 작성과 AI 초안 검토의 수정 항목·검토 시간을 비교한다.
- AI를 사용할 수 없어도 검증된 규칙으로 추천과 모의 승인이 가능하다.

## 6. 독립 평가와 합격 기준

### 6.1 정답 작성 방법

- 첫 카드 4종의 공식 약관을 선정한 뒤, 룰 엔진 구현 **전에** 대표 평가 사례 20개와 기대 결과를 고정한다.
- 개발자 1명이 공식 약관을 근거로 입력과 기대 결과를 작성하고, 다른 개발자가 계산과 약관 해석을 검토한다. 담당은 사례별로 교대할 수 있다.
- 기대 결과에는 카드별 할인 금액, 혜택 적용 여부, 추천 카드와 근거를 기록한다.
- 엔진이 출력한 값을 복사해 기대 결과로 삼지 않는다.
- 이후에는 매 실행마다 사람이 다시 계산하지 않고 자동 테스트가 엔진 결과를 고정된 기대 결과와 비교한다.
- 공식 약관 해석이나 규칙이 변경되면 변경 근거를 기록하고 해당 기대 결과를 다시 검토한다.

### 6.2 평가 사례

대표 사례 20개에는 다음을 포함한다.

- 정상 할인
- 전월 실적 미달과 충족
- 실적 제외 거래
- 최소 결제금액 미달
- 업종·결제 방식 불일치
- 월 혜택 한도 잔여와 소진
- 적용 가능한 혜택 없음
- 동률
- 기준 기간 경계
- 거래 취소
- 약관 적용 기간 만료
- 현재 주문 혜택 최대 카드와 월간 총혜택 최대 카드가 다른 상황

별도로 주문 금액·날짜·업종·결제 방식, 원장 거래, 예정 소비, 보유 카드 또는 대표 카드 설정을 바꾸는 **입력 변경 시험 10개**를 작성한다. 변경이 반드시 추천 카드 변경을 일으켜야 하는 것은 아니다. 결과가 유지되거나 달라지는 이유를 검증한다.

### 6.3 합격 기준과 보고

- 대표 사례 **20개 모두**에서 할인 금액, 혜택 적용 여부, 추천 카드가 독립적으로 검토한 기대 결과와 일치해야 한다.
- 입력 변경 시험 **10개 모두**에서 새 입력에 대한 계산 결과와 근거가 기대 결과와 일치해야 한다.
- 동일한 입력·원장·규칙 버전에서는 동일한 결과가 나와야 한다.
- 카드 4종과 예정 소비 최대 5건을 사용하는 개발 환경의 추천 API 응답 목표는 **2초 이내**다. 측정 환경, 실행 횟수, 결과를 함께 기록한다.
- 현재 주문 혜택만 최대화하는 방식과 BeONE의 월간 총혜택 최적화 방식의 결과를 같은 입력에서 비교한다.
- AI 약관 초안의 필드별 정확성, 사람의 수정 항목, 검토 시간 및 수동 작성 시간을 카드 4종에 대해 기록한다.
- 성공 사례뿐 아니라 실패 사례와 해결 여부도 최종 평가 자료에 포함한다.

## 7. 보안과 표시 원칙

- 실물 카드번호, CVV, 카드 비밀번호, 계좌정보를 일반 서비스 흐름에서 수집·저장하지 않는다.
- CODEF 연결 비밀번호는 연결 요청에만 사용하고 DB·로그·브라우저 저장소에 남기지 않는다.
- CODEF 키·토큰은 서버에서 관리하고 Android 앱에 포함하지 않는다.
- 실제 CODEF 응답 전문과 개인 거래내역을 저장소 또는 공개 평가 자료에 포함하지 않는다.
- 실제 보유 카드, 가상 보유 카드, 실제 조회 거래, 수동 입력 거래, 모의 거래를 화면과 데이터에서 구분한다.
- `실제 조회`, `사용자 확인`, `규칙 기반 추정`, `가상 데이터`, `미확인`의 출처와 신뢰 수준을 표시한다.
- 예상 혜택을 카드사가 실제 지급한 혜택으로 표현하지 않는다.
- 결제 관련 화면에 실제 금융거래가 발생하지 않음을 명시한다.
- Android 생체인증·PIN 인증을 카드사 인증 또는 실제 금융거래 승인으로 표현하지 않는다.

## 8. 구현 순서와 선행 확인

### P0. 범용 계산 흐름

- 첫 신용카드 2종·체크카드 2종과 공식 약관 선정
- CODEF 조회 상품과 최소 1종 이상 매핑 가능한지 확인
- 검증된 규칙 및 거래 원장 모델
- 독립 평가 사례 20개와 입력 변경 시험 10개의 기대 결과 고정
- 편집 가능한 주문과 수동 카드 상태 입력
- 가상 포트폴리오, 결정론적 계산·최적화, 모의 승인·취소
- 독립 평가와 임의 입력 변경 검증

### P1. 필수 통합

- KB국민카드 CODEF 조회·정규화·사용자 카드 매핑
- 실제 Android 기기에서 WebView·네이티브 생체인증·기기 PIN·60초 화면
- AI 약관 초안 추출·사람 검증과 수동 작성 방식 비교

P0와 P1은 **모두 MVP 완료 대상**이다. 구분은 개발 순서일 뿐이다. CODEF 상품 매핑과 Android 인증은 일정 위험이 크므로 P0 개발과 병렬로 기술 검증을 시작한다.

## 9. 현재 확인된 사실

- CODEF 데모 계정과 KB국민카드 계정을 확보했다.
- KB국민카드 보유카드, 승인내역, 실적조회, 청구내역, 한도조회 API의 개별 응답 테스트에 성공했다.
- CODEF 계정에서 `올라운드 티타늄카드`(신용)와 `nori 체크카드(RF)`(체크)가 조회됐다.
- 개별 API 응답 성공은 서비스 내부 상품 매핑, 월간 상태 해석, 추천 엔진 통합 완료를 뜻하지 않는다.
- 특정 실물 카드에 대해 자금 이동 없이 카드사 승인 응답을 받는 접근 가능한 API는 확인되지 않았다. 이번 MVP는 자체 모의 승인을 사용한다.

## 10. 최종 완료 조건

- [ ] 공식 약관을 검증한 신용카드 최소 2종과 체크카드 최소 2종의 `VERIFIED` 규칙을 사용한다.
- [ ] CODEF 실제 보유 상품 중 최소 1종을 검증된 내부 상품에 매핑한다.
- [ ] 예시 주문 수정 또는 임의 주문 생성 후 동일 엔진으로 추천한다.
- [ ] 내 카드 모드와 가상 포트폴리오 모드를 분리하고 동일 계산 엔진을 사용한다.
- [ ] 가상 원장으로 실적·혜택 상태를 산출하고 거래 변경·취소 후 다시 계산한다.
- [ ] 수동 입력만으로 카드 설정, 주문 생성, 추천, 모의 승인·취소까지 진행한다.
- [ ] KB국민카드 CODEF 조회값이 사용자 확인과 내부 매핑을 거쳐 같은 엔진에 입력된다.
- [ ] 미확인 실적·혜택 상태는 추정 또는 미확인으로 표시하고 필요한 확인을 받는다.
- [ ] 실제 Android 기기에서 생체인증 또는 기기 PIN, 60초 활성화, 만료·재인증이 동작한다.
- [ ] 결제 전 자동 추천 또는 대표 카드 고정 설정에 따라, 결제 중 카드 변경 없이 모의 승인한다.
- [ ] 승인 직전 최신 주문·상태를 재확인하고 중복 승인·취소를 방지한다.
- [ ] 독립 정답을 가진 대표 사례 20개와 입력 변경 시험 10개를 모두 통과한다.
- [ ] 카드 4종·예정 소비 최대 5건 조건의 추천 API 응답 목표를 개발 환경에서 확인한다.
- [ ] 모든 추천에서 입력·데이터 출처·적용 약관·규칙 버전·선택 이유를 확인할 수 있다.
- [ ] AI 약관 초안의 사람 검증을 시연하고 카드 4종에 대한 수정 항목·검토 시간을 수동 방식과 비교한다.
- [ ] CODEF·AI 실패 시에도 수동 입력과 검증된 규칙으로 핵심 흐름이 유지된다.
- [ ] 실제 금융거래를 발생시키지 않으며 모의 승인을 카드사 승인으로 오인하게 하지 않는다.
- [ ] 민감한 카드·계정 정보와 실계정 응답 전문을 저장하거나 로그에 남기지 않는다.

## 11. 구현 전 미결 결정
