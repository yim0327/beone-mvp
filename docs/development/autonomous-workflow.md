# 장기 연속 개발 운영 규칙

이 문서는 BeONE을 **백엔드**와 **Android** 두 작업선으로 나눠, 각 세션이 사용자 확인을 자주 기다리지 않고 이어서 개발할 때 따르는 공통 규칙입니다. 담당별 시작 프롬프트는 [백엔드](backend-start.md)와 [Android](android-start.md) 문서에 있습니다.

## 1. 적용 범위와 우선순위

- 사용자가 세션의 작업 지시로 **장기 연속 개발 모드**의 시작이나 재개를 명시적으로 요청한 경우에만 적용합니다. 담당별 시작 프롬프트를 작업 지시로 전달받은 경우가 여기에 해당합니다.
- 이 문서나 시작 프롬프트를 읽거나 검토·수정하라는 요청은 모드 시작이 아닙니다.
- 이 모드가 아닌 일반 작업에는 적용하지 않습니다. 일반 작업의 커밋·push·PR은 [CLAUDE.md](../../CLAUDE.md) 작업 원칙에 따라 사용자가 요청할 때만 합니다.
- 다음 문서의 규칙은 이 모드에서도 그대로 유지됩니다. 이 문서는 그 위에 자동으로 해도 되는 범위를 더할 뿐, 기존 규칙을 느슨하게 만들지 않습니다.
  - 요구사항: [PRD](../PRD.md), [결정 기록](../decisions.md)
  - 절차: [기여 가이드](../../CONTRIBUTING.md), [코드·테스트 컨벤션](../conventions.md), [README](../../README.md)
  - 보안: [CLAUDE.md](../../CLAUDE.md)의 보안 절, [PRD §7](../PRD.md#7-보안과-표시-원칙)
- 문서끼리 충돌하면 더 제한적인 쪽을 따르고, 충돌 지점을 진행 기록의 `사용자 확인 사항`에 적습니다.

## 2. 권한

### 자동으로 해도 되는 일 (자기 담당 범위 안에서만)

- 관련 자료 조사. 공식 문서·명세를 우선하고 출처와 버전을 기록합니다.
- 기능 이슈 생성과 `develop` 기준 작업 브랜치·전용 worktree 생성
  - 이슈에는 저장소 이슈 템플릿을 사용합니다.
  - 라벨은 템플릿이 정한 라벨과 [기여 가이드](../../CONTRIBUTING.md)의 영역 라벨(`backend`·`android`) 중 해당하는 것만 붙입니다.
- 구현, 테스트, 해당 기능에 필요한 문서 작성
- 내부 리뷰와 독립 리뷰 요청, 지적 사항 확인, 수정, 재검증
- 작은 논리 단위 커밋
- 자기 feature 브랜치에 대한 일반 push
- 충돌 해결을 위해 최신 `origin/develop`을 자기 feature 브랜치에 **merge**하는 것. rebase나 강제 push는 하지 않습니다.
- `develop` 대상 PR 생성과 갱신. draft PR을 ready for review로 바꾸는 것도 포함하며, 조건은 8절에 있습니다.
- 완료 상태를 기록한 뒤 실행할 수 있는 다음 독립 작업 선택

### 자동으로 하지 않는 일

- PR 병합(PR을 `develop`·`main`에 병합하는 것), 자동 병합 설정. 위 허용 목록의 `origin/develop` → 자기 feature 브랜치 merge는 여기에 해당하지 않습니다.
- `develop`·`main` 직접 수정·push
- 강제 push, 이미 만든 커밋의 이력 변경(rebase·reset·amend), 훅 우회(`--no-verify`)
- 다른 작업자의 변경, 기존 stash·백업 삭제나 덮어쓰기
- `frontend/`의 코드·설정·의존성·생성물 변경, 프런트엔드 빌드 실행이나 그 산출물 복사
- 공식 약관 해석 확정, 실제 상품 규칙의 `VERIFIED` 승격
- 미확인 값을 0원이나 임의의 기간(달력 월, 주문일 등)으로 대체
- 기존 공개 API·WebView 브리지 계약의 호환성을 깨는 변경
- 구현 결과에 맞춘 PRD·결정 기록·평가 기대값·fixture 변경
- 파괴적 DB 작업(기존 컨테이너·볼륨·데이터 삭제나 초기화)
- 실계정 데이터 공개, 비밀값 출력
- 새 유료 서비스 도입, 추가 과금 승인, 계정 로그인이나 가입, 요금제·계정·권한·저장소 설정 변경. 이미 사용자가 승인한 CLI·리뷰 도구는 기존 승인 범위에서 사용할 수 있습니다. 이 문구는 새로운 유료 도구 사용이나 기존 예산·사용 한도 확대를 승인하지 않습니다.
- 실제 결제나 카드사 승인 요청

### 스스로 정할 것과 사용자에게 물을 것

작은 구현 결정은 질문하지 않고 컨벤션에 맞게 정한 뒤 진행 기록에 남깁니다. 다음은 사용자 결정이 필요합니다.

| 스스로 정함 | 사용자 결정이 필요함 |
| --- | --- |
| 내부 클래스·메서드 이름과 구조, 테스트 구성, 비공개 보조 코드, 커밋 단위 | 혜택 계산·기간·한도·중복 적용 같은 금융 정책, 약관 해석 |
| 이미 확정된 계약 안의 구현 방식 | 공개 API·브리지 계약의 확정이나 변경 |
| 문서의 설명 방식 | PRD·결정 기록·평가 기대값의 변경, 범위 추가 |
| 의존성의 버전 선택(안정판, 출처 기록) | 새로 비용이 드는 도구, 예산·사용 한도 확대, 새 외부 서비스, 보안 정책 예외 |

사용자 결정이 필요한 항목을 만나면 그 부분만 보류합니다. 질문과 권장안을 진행 기록의 `사용자 확인 사항`과 관련 이슈 또는 PR에 남기고, 그 결정에 의존하지 않는 다른 작업을 계속합니다.

## 3. 작업 위치와 파일 소유권

| 작업선 | 수정할 수 있는 경로 |
| --- | --- |
| 백엔드 | `backend/**`, 백엔드 도메인 문서 `docs/domains/<도메인>.md`, `docs/backend/**`, `docs/progress/backend/**` |
| Android | `android/**`, `docs/android/**`, `docs/progress/android/**` |

- `frontend/**`는 두 작업선 모두 수정하지 않습니다.
- 그 밖의 문서는 공용 문서이며 기본적으로 읽기 전용입니다.
- [CLAUDE.md](../../CLAUDE.md)의 문서 유지 규칙 때문에 공용 문서를 고쳐야 하면, 자기 모듈을 설명하는 절만 최소로 수정합니다.
  - 수정할 수 있는 공용 문서: `README.md`, `docs/architecture.md`, `docs/api.md` 등
  - 상대 모듈의 절, 파일 전체 재포맷, 공통 계약은 바꾸지 않습니다.
- 다음은 자기 절 수정 대상이 아닙니다. 고칠 필요가 있으면 수정하지 않고 사용자 확인 사항으로 올립니다.
  - 요구사항·결정: `docs/PRD.md`, `docs/decisions.md`
  - 평가·조사 자료: `docs/evaluation-casebook.md`, `docs/card-benefit-research.md`, `fixtures/**`
  - 실기기 기록: `docs/d08-biometrics-poc.md`
  - 운영 규칙: `docs/development/**`, `CLAUDE.md`, `CONTRIBUTING.md`, `docs/conventions.md`
- 상대 작업선이 같은 절을 수정 중이거나 수정이 공통 계약에 닿으면, 그 수정만 보류하고 진행 기록과 PR에 조정 요청을 남깁니다.
- 두 작업선은 처음부터 서로 다른 작업 공간·브랜치·worktree를 사용합니다. 같은 폴더나 같은 브랜치를 두 세션이 함께 수정하지 않습니다.
- CLI로 git worktree를 만들었다고 작업 공간 관리 화면의 workspace가 자동으로 생기거나 전환된다고 가정하지 않습니다.
  - 파일 작업과 Git 명령은 대상 worktree의 경로를 명시해 실행합니다.
  - 새 작업을 시작할 때와 명령을 실행하기 전에 `pwd`, 현재 브랜치, `HEAD`를 확인합니다.
- worktree 폴더는 기존 작업 공간과 같은 상위 폴더에 브랜치 이름의 `/`를 `-`로 바꾼 이름으로 만듭니다(예: `feat-21-order-benefit`). 같은 이름이 이미 있으면 덮어쓰지 않고 다른 이름을 씁니다.

## 4. 시작·재개 점검

세션을 시작하거나 재개할 때마다 다음을 순서대로 확인합니다.

1. `git fetch origin`(`--prune` 같은 정리·삭제 옵션 없이)으로 최신 원격을 확인하고 최신 `origin/develop` SHA를 기록합니다.
   - 이 문서가 최신 `origin/develop`에 없으면 모드를 시작하지 않고 사용자에게 보고합니다.
2. 열린 이슈와 PR 중 자기 작업선 것의 상태를 확인합니다: 병합 여부, 진행 중인 작업, 리뷰 의견, 검증 상태, 차단 사유.
3. 실제로 이어갈 작업과 대상 worktree를 고릅니다.
   - 병합되지 않은 작업을 재개하면 그 작업의 기존 worktree를 고릅니다.
   - 병합 뒤 새 작업을 하면 최신 `origin/develop`에서 새 기능 브랜치와 전용 worktree를 만듭니다. squash 병합된 기존 브랜치를 pull·merge·rebase해서 다시 쓰지 않습니다.
4. 고른 worktree에서 경로·브랜치·`HEAD`·`git status`를 확인합니다.
   - 출처를 모르는 변경은 건드리지 않고 기록합니다.
   - 브랜치를 바꾸거나 파일을 덮어써서 문제를 피하지 않습니다.
5. 그 worktree의 기준 문서 5개를 최신 `origin/develop`과 비교합니다. 이전 작업 공간이나 병합된 옛 브랜치를 비교하지 않습니다.
   - 대상: `CLAUDE.md`, `docs/development/autonomous-workflow.md`, `docs/development/backend-start.md`, `docs/development/android-start.md`, `docs/decisions.md`
   - 기준은 1단계에서 기록한 `origin/develop` SHA로 고정합니다. 비교 중에 다시 fetch하거나 기준을 바꾸지 않습니다.
   - 파일마다 기준 커밋의 내용(`git show "<기준 SHA>:<파일>"`)과 worktree의 실제 파일을 `cmp`로 바이트 단위 비교합니다. tracked·untracked 여부와 관계없이 같은 방식으로 비교하고, 마지막 줄바꿈 등 내용을 정규화하지 않습니다.
   - 고른 worktree의 최상위에서 `PUT_SHA_HERE`를 기록한 SHA로 바꿔 bash로 실행합니다. 괄호는 하위 셸이라 `exit`가 현재 셸을 닫지 않습니다. 종료 코드 `0`은 5개 모두 일치, `1`은 누락·차이·조회·읽기 오류, `2`는 기준 SHA나 임시 디렉터리 오류입니다.

     ```bash
     (
       base=PUT_SHA_HERE
       git rev-parse --verify --quiet "$base^{commit}" >/dev/null || { echo "기준 조회 오류: $base"; exit 2; }
       tmp=$(mktemp -d) || { echo "임시 디렉터리 생성 오류"; exit 2; }
       result=0
       for f in CLAUDE.md docs/development/autonomous-workflow.md docs/development/backend-start.md docs/development/android-start.md docs/decisions.md; do
         if ! git cat-file -e "$base:$f" 2>/dev/null; then echo "기준에 없음: $f"; result=1
         elif [ ! -f "$f" ]; then echo "worktree에 없음: $f"; result=1
         elif ! git show "$base:$f" > "$tmp/base"; then echo "기준 조회 오류: $f"; result=1
         else
           cmp -s "$tmp/base" "$f"
           case $? in
             0) echo "일치: $f" ;;
             1) echo "내용 차이: $f"; result=1 ;;
             *) echo "읽기 오류: $f"; result=1 ;;
           esac
         fi
       done
       rm -rf "$tmp"
       exit "$result"
     )
     ```

   - 기준 내용은 파이프로 넘기지 않고 전용 임시 디렉터리의 파일에 저장합니다. 그래야 `git show` 실패를 `cmp` 결과와 구분할 수 있고, 명령 치환처럼 마지막 줄바꿈이 사라지지 않습니다. 임시 디렉터리는 비교 뒤 지우며, 저장소 파일·index·브랜치는 바꾸지 않습니다.
   - `git diff --name-status <기준 SHA> -- <위 5개 파일>`은 tracked 파일의 차이를 보는 보조 진단으로만 씁니다. untracked 파일은 비교하지 않으므로 통과 판단에 쓰지 않습니다.
   - 최신 SHA 확인이나 존재 확인만으로 내용 비교를 대신하지 않습니다.
   - 기준 조회 오류, 파일 누락, 읽기 오류, 내용 차이 중 하나라도 있으면 모드를 시작·재개하지 않습니다. 차이 난 파일, 원인, 필요한 다음 행동을 사용자에게 보고합니다. 파일 덮어쓰기·reset·자동 동기화로 우회하지 않으며, 이 점검이 merge 권한을 넓히지 않습니다.
   - 기존 worktree의 기준 문서가 오래돼 멈추는 것은 의도한 안전 동작입니다.
   - 이 비교는 장기 연속 개발 모드의 시작·재개에만 적용합니다. 운영 문서 자체를 검토·수정하는 일반 작업은 이 비교로 차단하지 않습니다.
6. 문서가 일치할 때만 자기 작업선의 진행 기록 `docs/progress/<작업선>/README.md`를 읽고 구현·재개 절차로 넘어갑니다. 진행 기록이 아직 `develop`에 없으면 진행 중인 자기 브랜치의 것을 읽습니다.

## 5. 반복 절차

### 작은 단계

범위 확인 → 구현·테스트 → 내부 리뷰 → 수정·재검증 → 짧은 기록 → 커밋

- 같은 기능의 하위 단계는 같은 브랜치에 작은 커밋으로 쌓습니다.
- 커밋 하나는 하나의 논리 단위입니다. 실패하는 테스트를 남긴 채 커밋하지 않습니다.

### 기능 단위

최종 diff 검토 → 모듈 전체 검증 → push·PR → 독립 리뷰 → 지적 사항 확인·수정·재검증 → 상태 기록 → 다음 독립 작업

- 기능 하나는 하나의 이슈이자 하나의 PR입니다.
- 같은 요구사항 안에서 서로 의존하는 하위 단계는 한 기능으로 묶어도 됩니다(예: 같은 FR의 인증과 60초 상태). 지나치게 잘게 나눠 다음 단계가 모두 병합 대기에 걸리지 않게 합니다.

### 다음 작업 고르기

- 무관한 다음 기능을 같은 브랜치·PR에 이어 붙이지 않습니다. 새 이슈와 새 브랜치로 시작합니다.
- 선행 PR이 병합되지 않았으면 그 PR에 의존하는 작업을 쌓지 않습니다.
  - 선행 브랜치에서 새 브랜치를 따지 않고, 선행 PR에 기능을 더하지도 않습니다.
  - 대신 최신 `develop`만으로 진행할 수 있는 다른 독립 작업을 고릅니다.
- 실행할 수 있는 독립 작업을 모두 마쳤거나 남은 작업이 모두 병합 대기·리뷰 대기·사용자 결정·환경 차단이면, 진행 기록을 저장하고 정지합니다.
- 병합 대기, 리뷰 대기, 차단 상태를 완료로 표시하지 않습니다.

### 열린 PR끼리의 충돌

- 같은 작업선의 열린 PR들이 같은 파일(진행 기록 README, 빌드 설정 등)을 고쳐 충돌하면, 먼저 병합된 쪽을 기준으로 해결합니다.
  - 남은 PR의 브랜치에 최신 `origin/develop`을 merge해 충돌을 풀고 다시 검증합니다.
  - 상대 작업선이나 다른 사람의 변경은 그대로 둡니다.
- 진행 기록 README가 충돌하면 `develop`의 내용을 유지하고, 자기 PR에 해당하는 줄만 다시 반영합니다.

## 6. 리뷰

- **내부 리뷰:** 구현 세션이 직접 하거나, 구현 세션이 띄운 읽기 전용 하위 에이전트가 합니다. 가능하면 하위 에이전트를 사용합니다. 하위 에이전트의 리뷰도 내부 리뷰이며 독립 리뷰가 아닙니다.
- **독립 리뷰:** CodeRabbit이나, 사용자가 구현 세션과 별도로 시작한 리뷰 세션입니다. CodeRabbit은 [기여 가이드의 확인 절차](../../CONTRIBUTING.md#coderabbit-리뷰-확인)를 따릅니다.
  - draft PR에서도 실제 리뷰가 시작됐는지 먼저 확인합니다. 이미 진행 중이면 중복 요청하지 않습니다. 시작되지 않았고 기존 요청도 없을 때만 `@coderabbitai full review`를 한 번 요청합니다. 한도·장애로 시작되지 않으면 `리뷰 대기`로 기록하고 다른 독립 작업으로 이동합니다.
  - 후속 커밋 뒤에는 기여 가이드에 따라 해당 변경분의 증분 리뷰가 시작됐는지 확인합니다. 진행 중인 리뷰나 해당 변경분에 대한 기존 요청이 없을 때만 `@coderabbitai review`를 한 번 요청합니다. 전체 변경을 처음부터 다시 검토해야 할 때만 `@coderabbitai full review`를 사용합니다.
- 리뷰어에게 다음을 제공합니다.
  - 실제 diff와 base·head SHA
  - 요구사항(이슈, PRD·결정 기록의 해당 항목)
  - 검증 결과와 그 근거
- 리뷰 의견은 실제 코드로 맞는지 확인한 뒤 반영합니다. 반영하지 않는 의견은 이유를 답글로 남깁니다.
- 자기 점검을 외부 리뷰나 사람 승인이라고 쓰지 않습니다. 자동 요약 댓글이나 체크 성공만으로 코드 리뷰가 끝났다고 판단하지 않습니다.
- **반복 제한**
  - 같은 문제의 수정 시도는 최대 3회입니다.
  - 외부 상태(리뷰·CI 등) 확인은 대기 항목마다 3회 또는 10분 중 먼저 도달하는 쪽에서 멈춥니다.
- **제한에 도달하면**
  - 리뷰가 오지 않거나 리뷰 도구가 한도·장애로 동작하지 않으면 `리뷰 대기`로 기록합니다. 이것은 차단이 아닙니다.
  - 수정이 해결되지 않거나 환경 문제로 진행할 수 없으면 `차단`으로 기록합니다.
  - 어느 경우든 다른 독립 작업으로 이동합니다.
- 리뷰 수치나 커버리지를 맞추려고 불필요한 주석·코드를 추가하지 않습니다.

## 7. 검증

| 작업선 | PR 전 모듈 전체 검증(각 모듈 디렉터리에서 실행) |
| --- | --- |
| 백엔드 | `./gradlew test --rerun-tasks`, `./gradlew webTest --rerun-tasks`, `./gradlew integrationTest --rerun-tasks`, `./gradlew build --rerun-tasks` |
| Android | `./gradlew assembleDebug testDebugUnitTest lintDebug` |

- 작은 단계에서는 영향받는 테스트를 실행하고, PR 전에는 모듈 전체를 검증합니다.
- Android에서 빌드 타입이나 release 설정(WebView, 네트워크 보안, 디버그 기능)을 바꾸는 작업은 `./gradlew assembleRelease lintRelease`도 실행합니다.
- 결과를 다음 다섯 가지로 구분해 기록합니다. PR 템플릿의 결과 칸에도 이 중 하나를 적습니다.
  - 실제 실행
  - 캐시 재사용(`UP-TO-DATE`·`FROM-CACHE`)
  - 미실행
  - 실패
  - 환경 차단
- 테스트 제외, `@Disabled`·skip, 기대값 변경으로 실패를 숨기지 않습니다.
- 검증 뒤 내용을 바꾸면 영향받는 검증을 다시 실행합니다.
- 검증한 기준(기준 커밋 SHA와 미커밋 변경 여부)과 최종 커밋의 관계를 기록합니다.
- Docker·SDK·기기·권한 문제는 해당 검증만 차단 상태로 둡니다. 다른 검증과 작업은 계속합니다.
  - 기존 컨테이너·볼륨을 지우거나 초기화해 문제를 우회하지 않습니다.
- Android 계측 테스트는 실제 Gradle 태스크와 사용자가 승인한 기기 또는 에뮬레이터를 확인한 뒤에만 실행합니다.
  - 에뮬레이터(AVD) 생성과 SDK 구성요소 설치도 사용자 승인 뒤에 합니다.
- 실제 기기에서 확인해야 하는 인증 동작은 mock이나 에뮬레이터 결과로 완료 처리하지 않습니다.

## 8. Git·PR

- 브랜치 이름, 커밋 메시지, 이슈·PR 양식은 [기여 가이드](../../CONTRIBUTING.md)와 `.github/` 템플릿을 따릅니다.
- PR의 base는 `develop`이고, 본문에 `Closes #이슈번호`를 적습니다.
- 파일 경로를 명시해 stage합니다. `git add .`·`git add -A`로 무관한 파일을 함께 넣지 않습니다.
- 커밋에 AI `Co-Authored-By` trailer를 넣지 않고, PR 본문에 AI 공동 작성자 문구를 넣지 않습니다.
- 자기 feature 브랜치만 일반 push합니다(`--force`, `--force-with-lease`, `--all`, `--mirror` 사용 금지).
- PR의 draft 여부
  - 모듈 전체 검증이 끝나지 않았거나 구현이 완성되지 않았으면 draft로 열고, 본문에 미완료 항목을 적습니다.
  - 모듈 전체 검증까지 끝나면 ready for review로 열거나 전환할 수 있습니다. 독립 리뷰 상태는 본문에 적습니다.
- PR을 만들거나 갱신한 뒤 원격의 head SHA, base, head 브랜치, 본문을 다시 조회해 확인합니다.
- 리뷰어·담당자는 지정하지 않습니다. 라벨은 2절의 기준을 따릅니다.
- 이슈를 직접 닫거나 완료 처리하지 않습니다.
- PR 병합은 사용자 승인 대기입니다.

## 9. 진행 기록

사용자가 서비스가 어디까지 됐는지 쉽게 이해하도록 작업선별 진행 기록을 남깁니다.

```text
docs/progress/<작업선>/README.md          현재 상태 요약 (40줄 이내)
docs/progress/<작업선>/<이슈>-<slug>.md   작업별 단계 기록
```

### README (전체 40줄 이내)

- 지금 가능한 기능. 계산 기능, API, 화면·앱 연결 단계를 나눠 어디까지 연결됐는지 적습니다.
- 아직 안 되는 기능
- 현재 작업과 PR
- 사용자 확인 사항(결정이 필요한 질문과 권장안)
- 다음 작업
- 작성 날짜와 기준 커밋
- 각 내용이 작업 브랜치 상태인지 `develop`에 반영된 상태인지

### 단계 기록 (단계마다 6~10줄)

```text
### 2026-10-28 14:30 · 단일 주문 정률 계산 · 완료
- 한 일: 주문 한 건의 정률 할인액을 계산하는 기능을 만들었습니다.
- 서비스에서 달라진 점: 계산 결과가 0원과 `확인 필요`를 구분합니다(API·화면에는 아직 연결되지 않음).
- 검증: `./gradlew test --rerun-tasks` 실제 실행, 통과(기준 a64cecb + 미커밋 변경)
- 남은 제한: 여러 주문을 나눠 결제할 카드를 고르지는 못합니다.
- 다음: 대상 금액 상한 계산(#이슈)
```

- 클래스·메서드 목록이나 긴 작업 일지로 채우지 않습니다.
- 개발 도구나 창 구성 같은 작업 환경 설명은 넣지 않습니다.
- 기술 설명 문서(`docs/domains/`, `docs/backend/`, `docs/android/` 등)는 코드와 같은 PR에서 갱신합니다. 진행 기록만 고치고 구조·사용법 문서를 방치하지 않습니다.
- 커밋 전 기록에는 검증한 기준을 적습니다. 자기 커밋의 SHA를 기록에 넣으려고 커밋을 반복하지 않습니다. 커밋 후의 정확한 SHA와 PR은 이슈나 PR 댓글에 남깁니다.

## 10. 즉시 정지할 때

다음 상황에서는 진행 중인 작업을 멈추고 상태를 기록한 뒤 사용자에게 알립니다.

- 비밀값·실계정 데이터가 출력·커밋·push됐거나 그럴 위험을 발견함
- 다른 작업자의 변경을 덮어쓰거나 지울 수 있는 상황
- 자동 금지 작업을 하거나 우회하지 않고는 현재 작업을 안전하게 멈출 수도 없는 상황
- 사용자가 거부한 도구 실행을 같은 방식으로 다시 시도해야만 하는 상황

병합·리뷰·사용자 결정을 기다리는 것은 정지 사유가 아닙니다. 5절에 따라 그 작업만 보류하고 다른 독립 작업을 계속합니다.
