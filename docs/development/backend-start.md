# 백엔드 장기 연속 개발 시작 프롬프트

새 백엔드 세션을 시작하거나 재개할 때 아래 **프롬프트** 절 전체를 작업 지시로 전달합니다. 공통 규칙은 [장기 연속 개발 운영 규칙](autonomous-workflow.md)에 있으며, 이 문서는 백엔드 작업선에만 해당하는 내용을 담습니다.

---

## 프롬프트

BeONE 저장소(`yim0327/beone-mvp`)의 **백엔드 작업선**을 장기 연속 개발 모드로 시작(또는 재개)한다. 이전 대화 내용은 알 수 없다고 가정하고, 이 프롬프트와 저장소 문서만을 근거로 작업한다.

### 1. 먼저 읽을 문서

1. `docs/development/autonomous-workflow.md`: 권한, 파일 소유권, 시작 점검, 반복 절차, 리뷰·검증·Git 규칙. 이 문서를 반드시 따른다. 최신 `origin/develop`에 이 문서가 없으면 모드를 시작하지 않고 보고한다.
2. `CLAUDE.md`, `CONTRIBUTING.md`, `README.md`
3. `docs/PRD.md`, `docs/decisions.md`, `docs/conventions.md`, `docs/architecture.md`
4. `docs/domains/benefit.md`, `docs/api.md`, `docs/card-benefit-research.md`, `docs/evaluation-casebook.md`
5. `docs/progress/backend/README.md`. 없으면 첫 작업에서 만든다.

### 2. 담당 범위와 시작

- 담당 경로와 공용 문서 수정 기준은 운영 규칙 3절의 백엔드 행을 따른다. `frontend/**`와 `android/**`는 수정하지 않는다.
- `docs/api.md`는 공통 응답·오류 처리 계약이다. 전체 업무 API 명세가 아니며, 공통 계약은 바꾸지 않는다.
- 시작·재개 시 운영 규칙 4절의 점검을 한 뒤, 진행 중인 백엔드 PR의 리뷰 의견과 검증 상태부터 처리하고 아래 대기열로 넘어간다.

### 3. 작업 대기열

위에서부터 시작 조건을 만족하는 작업을 고른다.

1. **기존 계약으로 확정할 수 있는 순수 계산 하위 기능과 합성 테스트**
   - 순수 Java로 작성한다. Spring·HTTP·DB·`common.web`·CODEF·AI에 의존하지 않는다.
   - 예: 베이시스 포인트 요율 계산, 정액 계산, 건당 대상 금액 상한 적용, 최소 결제 금액·결제 방식·대상 업종·제외 업종 판정, 전월 실적 구간 선택(`ServiceTier`·`LimitTier`의 "이상" 기준), 원 미만 금액 발생 여부 판정
   - 근거는 모델 javadoc, `docs/decisions.md`, PRD에 명시된 것만 쓴다. 근거가 없는 조건은 `확인 필요`로 둔다.
   - 4절에서 미결인 결과 타입에 묶지 않는 독립 함수와 테스트로 만든다.
   - 합성 테스트에는 가상 카드 ID와 `example.invalid` 출처를 쓴다. 실제 카드 ID·상품명에 맞춘 분기를 만들지 않는다.
2. **실제 업무 명세가 확인된 API:** 수동 카드·상태·주문·예정 소비
   - **시작 조건**
     - 업무 API 명세(엔드포인트, 요청·응답 필드, 검증 조건)가 저장소나 사용자 제공 자료로 확인된다. 읽은 명세의 출처와 버전을 기록한다.
     - 사용자 식별 방식(D-09, 미결)에 의존하는 부분은 그 결정이 확정돼 있다.
   - 명세가 없으면 엔드포인트를 만들어 내지 않는다. 필요하면 `docs/backend/`에 `후보`로 표시한 명세 초안만 작성하고 사용자 확인 사항에 올린다.
3. **공식 명세 기반 CODEF 어댑터**
   - 대상: 오류 경계(연결 실패·인증 만료·매핑 실패 시 수동 입력 유지)와 비식별 합성 테스트
   - **시작 조건:** 로그인 없이 읽을 수 있는 CODEF 공식 개발 문서에서 해당 API 명세를 확인하고 출처·버전을 기록한다. 로그인이 필요하면 사용자 확인 사항으로 올린다.
   - 명세상의 필드는 매핑 후보다. 실제 응답으로 의미와 기간을 확인하기 전까지 상태 출처 분류를 확정하지 않는다(D-04). 실제 카드의 상품 매핑(D-01)은 `CANDIDATE`로 유지한다.
   - 실계정, 실제 키, 실제 응답 전문을 사용하거나 저장하지 않는다. 키가 필요한 실제 호출은 하지 않는다.
4. **선행 기능이 `develop`에 병합된 뒤에만 하는 작업.** 미병합 PR 위에 쌓지 않는다.
   - 원장 상태 산출·취소 재계산: 단일 주문 계산 결과 구조(4절)와 한도 차감 순서의 표현이 확정되고 구현이 병합된 뒤
   - 월간 최적화·추천: 원장 상태 산출이 병합된 뒤
   - 모의 승인: 추천과 해당 업무 API 명세가 준비된 뒤

### 4. 계산 결과 타입의 결정 상태

확정된 설계 방향의 기준 문서는 [D-13](../decisions.md#d-13-확정-정책)이다. 확정된 방향은 D-13을 따르고, 이 절과 다르면 차이를 보고한다. 미결 항목은 D-13의 미결 목록과 이 절의 표를 합친 것이다.

- **D-13이 확정한 것(요약):**
  - 방향: 신규 `OrderBenefit`으로 단일 주문 결과를 분리하고 기존 결과 타입의 의미는 유지한다. 조건 판정과 채택 여부(`ADOPTED`·`NOT_ADOPTED`·`UNDETERMINED`)를 나누고, 실제 기여액 `contribution`을 후보 금액과 구분한다.
  - 후보·결과 타입의 최소 계약(#29, `ServiceCandidate`·`OrderServiceBenefit`), 단일 서비스 후보 판정기 범위(#31), 카드 한 장의 후보 취합 분류(#33)
  - 카드 한 장·주문 한 건의 결정기 정책(#35, `develop` 병합): 한도 없는 비선택형 서비스만 판정, 규칙 사용 불가와 판정 결과 구분, 미확정 사유가 있을 때 `UNDETERMINED`·`확인 필요` 처리, 서비스 동률, 실적 정책 조건, 확정 0원 후보, 구조화된 미확정 사유(`PendingReason`)와 필수 실적 정책 근거(`PolicyTermEvidence`)
- **D-13에서도 미결:** `OrderBenefit`과 `CardBenefit`(`currentOrderBenefit`·`services`·`remainingLimits`)의 연결·매핑, 그 연결 시의 상세 불변 조건, 한도·선택형 서비스를 판정할 때의 채택·기여액, 카드 단위 사유 우선순위, 미확정 조건의 한도 차감액 반영, 중복 허용 서비스의 합산과 공유 한도 차감·배분, 아래 표의 미결 계산 정책. D-13 범위를 넘는 상세는 임의로 확정하지 않는다.

다음 정책은 기본 규칙이 이미 정해져 있다. 정해진 부분은 따르고, **결과 타입에서의 표현과 계산 통합 방식만** 임의로 확정하지 않는다.

| 항목 | 이미 정해진 부분 | 미결인 부분 |
| --- | --- | --- |
| 중복 적용 | 약관이 허용하지 않는 한 한 거래에는 가장 큰 단일 혜택만 적용(PRD FR-05, `BenefitService.stackableWith`). 근거가 없으면 `확인 필요`(D-03). 카드 한 장·주문 한 건 결정에서는 확정 양수 후보가 둘 이상이고 후보 쌍의 중복 관계가 미확정일 때 `확인 필요`(D-13, #35). 양수 후보가 하나면 중복 관계 때문에 막지 않음 | 중복 허용 서비스의 합산 계산, 중복 적용된 서비스끼리 공유 한도를 차감하는 순서. 중복 관계가 미확정이거나 중복 계산이 범위 밖일 때의 단일 주문 결과 표현은 D-13(#35)에서 정함 |
| 서비스 동률 | 카드 동률 규칙은 D-12. 같은 카드 안에서 후보 금액 최댓값이 같으면 서비스 ID의 `String.compareTo` 오름차순 첫 서비스를 채택(D-13, #35) | 없음(한도·선택형 서비스가 포함될 때의 채택은 아래 행과 D-13 미결을 따름) |
| 선택형 서비스 | 선택 서비스·변경 이력이 없으면 해당 할인은 계산하지 않음(D-03). 사용자 확인값은 `MANUAL`(D-04) | 결과 타입에 어떻게 포함하고 제외 근거를 어떻게 표현할지(#35 결정기는 지원 범위 밖으로 두고 카드 금액을 `확인 필요`로 둠) |
| 한도 차감 순서 | 카드별 순서(예: 첵첵은 전표 매입순서). 미확인이면 승인순서로 대체하지 않음(D-03) | 미확정 조건이 있을 때 한도 차감액에 어떻게 반영할지(카드 금액·기여액은 D-13 #35 결정을 따름) |
| 기간 | 카드별 실적·혜택 기간과 거래 기준일(D-03). 상태값의 출처·기준 기간(D-04) | 입력 상태값의 기간이 계산에 쓸 수 있는지 판정하는 규칙, `otherBucketsUsed`의 의미 |
| 신규 유예 | 카드별 유예 범위(D-03 표) | 계산과 결과에서의 표현 |
| 월 1회 | 노리 통신요금 2,500원 정액, 월 1회(D-10) | 월 1회를 어느 결제에 적용할지(D-10 한계). 현재 모델에는 횟수 제한 표현이 없음 |
| 카드 단위 사유 | 상태 코드 목록(`ApplicationStatus`) | 적용된 서비스가 없을 때 카드 사유의 우선순위 |

- 위 미결 부분이 필요한 구현만 보류하고, 질문과 권장안을 진행 기록의 `사용자 확인 사항`과 관련 이슈에 남긴다.
- 결정에 의존하지 않는 산술·판정 함수, 테스트, 명세가 확정된 다른 기능은 계속 진행한다.

### 5. 지켜야 할 경계

- 미확인 상태·규칙·금액을 0원이나 임의 기간(달력 월, 주문일)으로 대신하지 않는다. `BenefitAmount.NeedsConfirmation`과 `StateValue`의 `UNKNOWN`을 유지한다.
- 미확정 조건(`ConditionalTerm`)은 근거가 `CONFIRMED_ABSENT`일 때만 무시한다.
- 실제 상품 규칙을 `VERIFIED`로 승격하지 않고, 공식 약관 해석을 확정하지 않는다.
- 합성 테스트 통과를 실제 상품 검증이나 공식 평가 통과로 표현하지 않는다.
  - 평가 fixture(`fixtures/evaluation-cases.json`)는 `CANDIDATE` 규칙을 전제로 한다.
  - fixture 매핑 테스트 통과는 엔진 평가가 아니다.
- 기존 fixture의 입력·기대값·검증 상태와 PRD의 기대값을 수정하지 않는다.
- 계산 결과 상태와 API 오류 코드(`ApiErrorCode`)를 섞지 않는다. 도메인 코드는 `common.web`에 의존하지 않는다.
- 도메인·패키지·주요 클래스가 바뀌면 `docs/domains/` 문서와 `docs/architecture.md`의 백엔드 절을 같은 PR에서 갱신한다.
- 검증은 운영 규칙 7절을 따른다.
  - `integrationTest`와 `build`는 Docker가 필요하다. Docker를 쓸 수 없으면 그 검증만 환경 차단으로 기록한다.
  - 기존 컨테이너·볼륨·DB를 삭제하거나 초기화하지 않는다.

### 6. 정지와 보고

- 실행할 수 있는 독립 작업이 없으면 `docs/progress/backend/README.md`를 갱신하고 정지한다. 남은 작업이 병합 대기, 리뷰 대기, 사용자 결정, 환경 차단뿐인 경우도 같다.
- 정지할 때는 다음을 보고한다.
  - 완료한 작업과 PR
  - 실제로 실행한 검증과 그 결과
  - 리뷰 상태
  - 사용자 확인 사항과 권장안
  - 다음에 할 수 있는 작업
